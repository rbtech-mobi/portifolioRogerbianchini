SaaS backend and PWA

Multi Tenant Ordering Platform

An ordering and operations platform where multiple independent food businesses share the same deployment. Each tenant has isolated catalog, orders, users, branding and payment records. Tenant scoping is enforced on the server for every protected request, not on the client.

11 database tables 13 automated tests Node.js MySQL Firebase Auth
Technical Notes

Problem

Sharing infrastructure across tenants reduces cost and maintenance, but introduces a hard constraint: one business must never read, list or modify another business's data. Getting this wrong is not a bug, it is a data breach.

What I built

A public catalog, cart and order flow for end customers, and an installable admin PWA where each business manages its menu, order states, payments and branding.

Request flow

Express Request ID, security headers, rate limits and body size limits before any handler runs.
Identity Firebase verifies the ID token and attaches the authenticated user to the request.
Tenant context An admin user lookup resolves the business ID server-side, before any tenant-owned data is queried.
Service layer Order rules, allowed state transitions, database transactions and payment ledger logic.
Repository Parameterized SQL queries scoped by business ID on every tenant-owned table.

Key decisions

  • Money stored as integer cents to avoid floating point rounding.
  • Payments modeled as an append-only ledger, not as a mutable balance.
  • Order creation accepts an idempotency key to prevent duplicates on retry.
  • Uploaded images are decoded and rewritten by the server before storage.

Stack

Node.js, Express 5, MySQL, Firebase Auth, Zod, Sharp, Helmet, PWA with Service Worker, vanilla JavaScript on the client, node:test and Supertest.

Sales workflow and LLM integration

Outreach Calibrator

A prospecting assistant that combines CRM fields and free-text research into a structured LLM request, producing a first-message draft that a sales rep reviews and sends. Built to sit inside an SDR workflow, not to replace the rep.

monday.com webhooks LLM integration Structured prompts Workflow automation
Technical Notes

Problem

Personalized outreach requires research. High-volume outreach usually skips that research and produces generic messages. The gap is not writing skill, it is context.

What I built

A small application that receives prospect data from a monday.com webhook or from manual entry, merges it with research notes, and sends a structured payload to an LLM. The output is a suggested angle and a first-message draft.

Workflow

Input Prospect name, role, company, website, offer and research notes.
Ingestion monday.com webhook or native automation, with manual entry as a fallback path.
Analysis The prompt maps prospect context to the seller's value proposition and constrains the output format.
Output One suggested approach angle and one first-message draft. The rep reviews, edits and sends.

Design choices

  • The rep remains responsible for the final message. The tool does not send automatically.
  • Prompts are structured and versioned, not free-form.
  • The workflow runs inside monday.com so it fits the existing SDR routine.
  • Research notes are a required input, to avoid generic output.

Stack

LLM integration, monday.com webhooks, structured JSON payloads, workflow automation and prompt design.

Embedded device and MQTT workflow

Desktop Workflow Terminal

A touchscreen device for time-sensitive approvals. It receives a workflow message over encrypted MQTT, shows the request on a dedicated screen, and publishes the selected response back to the automation server.

ESP32 S3 C++ FreeRTOS MQTT over TLS n8n
Technical Notes

Problem

Approval requests sent through chat and email get missed. A dedicated physical device makes the request visible and gives the operator a direct, single-purpose response path.

What I built

Firmware for a WT32 SC01 Plus with a 3.5 inch touch display, dual WiFi failover, MQTT messaging, retained health status and a simple response interface.

Device flow

Connectivity Primary and secondary WiFi networks with automatic recovery on failure.
Messaging HiveMQ Cloud over TLS, QoS 1 for incoming and outgoing messages.
Interface Touch input over I2C and display rendering with LovyanGFX.
Workflow n8n publishes requests to the device and consumes the selected response.
Health A retained status topic reports device availability at a fixed interval.

Technical scope

  • State managed on-device, not on the server.
  • Encrypted MQTT with credentials stored outside the firmware.
  • Reconnection logic covers both WiFi and broker.
  • Physical interface intentionally minimal, one screen, one decision.

Stack

ESP32 S3, C++, FreeRTOS, MQTT, TLS, LovyanGFX, ArduinoJson, HiveMQ Cloud and n8n.
